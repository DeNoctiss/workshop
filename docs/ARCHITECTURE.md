Доменный движок не зависит от React или Dexie. Команда изменяет рабочую копию состояния, а адаптер БД проверяет и записывает её в одной транзакции. Ошибка не оставляет частично изменённый склад.

## Модель данных и границы

`State.schemaVersion = 3`. К существующим `materials`, `printers`, `projects`, `runs`, `movements`, `settings` добавлены:

- `userProducts`: личные справочные товары. Встроенный набор находится в коде, не в пользовательской базе.
- `projectNotes`: долговременные заметки с `projectId`.
- `runNotes`: заметки конкретного запуска с `runId`, временем и источником `internal` / `customer_reported`.
- `runTasks`: задачи с `runId`, порядком, готовностью и необязательным `sourceNoteId`.
- `boards`: одна доска на `projectId`; своя схема 1, ревизия, узлы, связи и viewport.

У `Run` появился необязательный `customer`. Рецепт и цены запуска по-прежнему защищены снимками. Задачи и заметки не вызывают складских движений и не переключают этапы.

`CatalogProduct` описывает товар и варианты упаковок. `Material` описывает реальный склад: единицу, упаковку, цену, порог и историю. В нём могут быть `productId`, `productSnapshot` и `packageId`. На доске `MaterialReference` хранит ID и компактный снимок подписи/артикула/цвета. Исчезновение товара из будущего каталога не уничтожает подпись. Добавление ссылки не создаёт расход.

`BoardData` — discriminated union по `kind`: image / note / checklist / group / material / palette / link / paint. Содержимое не хранится произвольным `any` в UI; неизвестный тип отвергается при импорте.

## Хранение, миграция и конкуренция

Имя БД **не менялось**: `masterskaya-v1`. Dexie-схема версии 3 содержит `states` (запись `main`), `assets` (Blob и метаданные), `assetIndex` (только метаданные). Главный экран не читает все изображения. Компонент `Photo` загружает необходимый Blob и освобождает object URL.

`migrateState` не изменяет входной объект. При v1 добавляет коллекции, переносит старый текст проекта в ленту и создаёт группы/карточки старых фото с существующими ID. При v2 поднимает номер схемы, при v3 возвращает копию без повторной миграции. Старые поля и бинарные данные сохраняются. Dexie upgrade выполняется транзакционно.

`mutate` сериализует read–modify–validate–write. Общая ревизия защищает формы от устаревшего состояния. Рецепт сравнивает `updatedAt`, зафиксированный при открытии; материал сравнивает исходную запись. Поэтому сохранение несвязанной заметки или доски не мешает редактировать материал, а изменение того же материала другой вкладкой вызывает конфликт.

Доска использует отдельную ревизию, а не общую ревизию склада. Автосохранение через 700 мс сохраняет JSON и ожидающие новые изображения атомарно. Номер поколения правок не позволяет пометить более свежий текст сохранённым после завершения предыдущего запроса. Навигация внутри приложения ждёт сохранения; закрытие вкладки предупреждает о несохранённых данных. Это не гарантия записи при аварийном закрытии браузера.

`BroadcastChannel` и локальное событие обновляют экраны других вкладок. Чистая доска принимает новую версию; при собственных несохранённых правках показывает конфликт. Восстановление ZIP поднимает ревизии досок выше старых значений, блокируя запись из устаревшей вкладки.

## Изображения, группы и копирование

Узлы содержат ID изображений, не base64. Новые файлы: JPG/PNG/WebP до 15 МБ, не больше 60 Мп, оригинал без уменьшения и WebP-превью до 480 px. Старые изображения остаются в том качестве, в котором были записаны старой версией.

Удаление узла не удаляет Blob. `removeAsset` отказывает, если файл используется узлом или обложкой. При копировании проекта создаются независимые ID файлов, доска и заметки; производства и их договорённости не копируются.

Группы одного уровня. `position` ребёнка относительна группе. `absolutePosition`, `groupNodes` и `ungroupNodes` сохраняют мировые координаты; копирование переназначает ID и связи. В историю undo не попадают Blob. Сериализация отбрасывает выделение, dragging и измерения React Flow, сохраняя размеры в `style`.

## Деньги, склад и формулы

Денежные значения — целые копейки. Количества округляются до 0.001 базовой единицы; конвертации г ↔ мл нет.

- Доступно = физический остаток − резерв.
- Физический остаток = приходы + корректировки − расход − брак.
- Резерв = резервирования − освобождения.
- Расход на экземпляр = норма × число экземпляров; общий расход партии учитывается один раз на запуск.
- Компонент смеси = объём × число экземпляров × (1 + потери / 100) × доля / сумма долей.
- Электричество = часы × Вт / 1000 × тариф.
- Амортизация = часы × стоимость оборудования / ресурс в часах.
- Обслуживание = часы × ставка обслуживания.
- Ручной труд = часы × ставка.
- Общая стоимость = материалы + электричество + амортизация + обслуживание + труд + прочее.

Уровень запасов определяется **доступным**, а не физическим остатком. Красный: `available <= minimum`. Верхняя граница жёлтого: `max(packageQty × 0.5, minimum + max(packageQty × 0.1, 0.001))`. Выше неё — зелёный. Так жёлтая зона остаётся чуть выше заданного минимума, даже если он больше половины упаковки. Шкала процентов по-прежнему относится к объёму одной упаковки.

## ZIP

`manifest.json`: format `masterskaya`, version 3, schemaVersion 3, дата, количество фото. `data.json`: состояние и метаданные файлов. `images/<projectId>/<assetId>.image` и `.thumb`: бинарные файлы.

Импорт принимает форматы 1, 2 и 3, мигрирует старую схему, проверяет всё состояние, журнал, ссылки, размеры, уникальность ID и наличие изображений. Затем `replaceAll` атомарно заменяет все три таблицы. Экспорт использует единый транзакционный snapshot. ZIP ограничен 150 МБ сжатого / 300 МБ распакованного содержимого.

## Как расширять

Новый тип карточки: добавить вариант в `BoardData`, валидатор, редактор `NodeEditor`, отображение `BoardCard` и действие добавления. При несовместимой структуре обновить схему доски и явную миграцию, затем тест старого ZIP. PaintNode уже использует ссылочные PNG-маски; сохраняйте этот принцип для новых эффектов.

Новая категория товара: расширить `Category`, `categories`, `ProductProperties`, `propertyFields`, единицы и валидатор. Новый встроенный ассортимент — через пайплайн, описанный в `CATALOG-SOURCES.md`; личные товары — через UI.

Новая операция производства: не обходить существующие резерв/finish. Потребуется согласованная миграция плана и снимков; обычная FDM/SLA печать должна остаться удобным частным сценарием. Это следующий этап, а не скрытое поведение текущего движка.

При появлении backend заменить адаптер `data/db.ts`. На сервере команды запуска/завершения должны быть одной транзакцией с проверкой версий, резервов и idempotency key. Нельзя переносить клиентское чтение/изменение/запись как несколько независимых HTTP-запросов.

## Дополнения 0.5

`ProjectNote` и `RunNote` имеют необязательный `attachmentIds`. `mutateWithAssets` сохраняет заметку и подготовленные файлы одной транзакцией с проверкой принадлежности проекту. `referencedAssetIds` защищает файлы заметок, маски и исходники перекраски от удаления. При копировании проекта ID вложений, документов и масок переназначаются.

`PaintDocument` хранится в `BoardData.kind = "paint"`: исходник, preview, рабочие размеры, слои. Слой содержит имя, PNG-маску по `maskAssetId`, цвет, видимость, opacity, blend и необязательный снимок материала. Сырые массивы пикселей существуют только в памяти редактора. `Asset.purpose` различает `note`, `paint-mask`, `paint-preview`; производные изображения скрыты из обычной галереи.

`src/paint/mask.ts` содержит чистые функции кисти, flood fill и растушёвки. Flood fill четырёхсвязный, с очередью вместо рекурсии; RGB-расстояние сравнивается с `3 × tolerance²`. `selection.worker.ts` получает рабочие RGBA один раз и возвращает маску transfer-буфером. Кисть переводит координаты указателя через размер canvas в пиксели изображения, интерполируя точки вдоль движения.

`canvas.ts` собирает видимые слои в порядке снизу вверх. Сначала используется непрозрачная RGB-основа, затем маски и режимы Canvas 2D, в конце накладывается исходный alpha через destination-in. Это предотвращает повторное умножение полупрозрачного края. Кэш цветных масок пересоздаётся при изменении маски/цвета; удалённые слои освобождаются из кэша.

Каждое сохранение создаёт новые маски/preview, чтобы undo доски и копии не зависели от последующих изменений. Старые производные файлы автоматически не очищаются: это сознательная граница текущей версии, требуется отдельная сборка мусора с учётом истории. Редактор ограничен 2048 px по длинной стороне и 12 слоями.

`domain/inventory.ts` сначала валидирует все строки и сверяет `expectedPhysical`, затем создаёт корректировки. Проверка и запись вызываются внутри `mutate`: ни частичного применения, ни потери резервов. Черновик UI хранится в sessionStorage этой вкладки, а подтверждённая сверка — в журнале IndexedDB.

`dropIntoGroups` сравнивает центр карточки с телом группы и пересчитывает относительные координаты, сохраняя мировую позицию. `data.direction` у связи принимает forward/reverse/both/none. Стрелки — визуальная связь, они не запускают производственные операции.


## Дополнение 0.6

Состояние `State.shopping?` хранит конфигурацию и список закупок; создание/пересчёт и приход проходят существующую транзакцию `mutate`. `validateShopping` проверяет структуру и связь прихода с журналом. Внутренняя схема нового `PaintDocument` — 2; прежние документы без номера поддерживаются. Объяснение модулей и формул: UPDATE-0.6.md.
